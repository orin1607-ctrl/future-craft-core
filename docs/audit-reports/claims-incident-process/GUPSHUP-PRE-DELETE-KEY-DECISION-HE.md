## 2) האם אחד מהם בשימוש ב-Staging?

**Staging משתמש במפתח אחד פעיל** — Secret בשם `GUPSHUP_API_KEY` (אורך 35, מאומת עכשיו).

**אי אפשר לזהות אם זה «מפתח 1» או «מפתח 2» בטבלת הפורטל.**

סיבות עובדתיות:
- ערך ה-Secret ב-Staging **לא קריא** (Management API = שמות בלבד)
- אין hash / prefix / fingerprint / partial של אף מפתח פורטל בריפו
- אין לוג «Staging = key #N»

השערה ישנה («account-level מוסתר») **לא הוכחה** ואינה בסיס להחלטת מחיקה.

**לא. אין אישור למחוק «API Key מספר 1» או «API Key מספר 2».**

אין בפרויקט מיפוי מספר↔שימוש. כל בחירה לפי מספר תהיה ניחוש — וביקשת במפורש לא לנחש.

## 4) הערכת סיכון מדויקת (לכל אחד — זהה מהפרויקט)

למחיקת **מפתח מספר 1** ולמחיקת **מפתח מספר 2** הסיכון מהנתונים שיש לנו **זהה**, כי אין מזהה שמפריד ביניהם:

| תרחיש אפשרי | הסתברות מהפרויקט | השפעה על Staging אם מוחקים את המפתח הלא-נכון |
|-------------|------------------|-----------------------------------------------|
| Staging = אחד משני מפתחות ה-App בטבלה | **לא ידוע** (לא ניתן לחשב) | WhatsApp Staging נשבר מיד (`gupshup_verified` ייכשל) עד שמעדכנים את Secret ב-Staging למפתח החדש |
| Staging = מפתח account-level שלא בטבלה | **לא ידוע** (לא ניתן לחשב) | מחיקת מפתח App בטבלה **לא** תשבור Staging |
| שני מפתחות ה-App לא בשימוש ב-Staging | **לא ידוע** | מחיקה בטוחה ל-Staging |

**מה שכן ידוע בוודאות:**
- Staging **תלוי** בערך Secret נוכחי שעובד מול Gupshup עכשיו.
- מחיקת **המפתח שמאחורי ה-Secret** תשבור Staging עד החלפה.
- מחיקת מפתח **אחר** (שאינו ב-Secret) לא תשבור Staging.
- **אנחנו לא יודעים** איזה משני מספרי הפורטל הוא זה שב-Secret.

לכן: סיכון לכל מספר = «עלול להיות המפתח של Staging או לא» — **בלי יכולת לדרג 1 מול 2 מהפרויקט.**

## 5) אישור מפורש — מה מותר / מה אסור

### אסור
- למחוק «מפתח 1» או «מפתח 2» על סמך מספר בלבד.
- לנחש לפי תאריך בלי מיפוי פורטל→Staging.

### מותר רק אחרי אחד מאלה

**מסלול A (מועדף) — מטא-דאטה מהפורטל, בלי ערכי מפתח:**  
שלח לי (טקסט בלבד):

```text
מפתח 1: Created=… ; Last used=… / אף פעם ; ID/suffix אם מוצג=…
מפתח 2: Created=… ; Last used=… / אף פעם ; ID/suffix אם מוצג=…
```

אם יש **Last used** על אחד בלבד — זה המועמד היחיד שיכול להיות Staging; **לא אאשר למחוק אותו**. אאשר למחוק את השני (זה שאין עליו שימוש).

אם אין Last used לשניהם — עדיין אין מיפוי; נשאר מסלול B.

**מסלול B — רוטציה מבוקרת (אם חובה למחוק כדי ליצור, ואין Last used):**  
אין אישור למספר ספציפי. יש אישור ל**נוהל** בלבד:

1. פתח מראש את Staging Secrets:  
   https://supabase.com/dashboard/project/usfeoerkpcafxxlyuldl/settings/functions  
2. מחק **אחד** מהמפתחות (בחירה שרירותית — קבל ש-Staging עלול לרדת לדקות).  
3. מיד Create → העתק את הערך החדש (פעם אחת).  
4. **תוך דקות:** הדבק כ-`GUPSHUP_API_KEY` ב-**Staging** → שמור.  
5. בדוק חיבור Staging (או כתוב לי «עדכנתי Staging» — נריץ probe).  
6. רק אחרי Staging ירוק — אותו מפתח ל-Production.  
7. את המפתח הישן השני אפשר למחוק מאוחר יותר אם צריך מקום.

חלון הסיכון במסלול B: ממועד המחיקה עד עדכון Staging — WhatsApp Staging עלול להיות שבור **אם** מחקת את המפתח שבשימוש.

**מסלול C — Support:** לבקש מהם לזהות איזה key active / unused לפי App ID, או לאפשר Create בלי מחיקה.
